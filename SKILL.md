# Twilio Workshop Agenda Generator

Produces a single self-contained HTML file for a technical workshop/hackathon agenda, presented as a **paginated slide deck** — one full-viewport section per screen, Next/Prev buttons plus arrow-key navigation, a dot indicator, a slide counter, and a collapsible left-hand slide menu (open by default).

Visual identity is **"Paper"** — warm cream background, Fraunces serif headings paired with IBM Plex Sans body text and IBM Plex Mono for timestamps/labels/code, a dotted timeline, and a tilted stamp-style section label (`.eyebrow`). Color-coded session types: talk = dusty blue, build = terracotta (primary accent), planning = ochre, retro = violet.

Navigation is buttons and arrow keys only (no wheel/scroll-to-advance). Long slides scroll internally via plain `overflow-y: auto`. Theme, print behavior, and navigation JS all live in `templates/agenda-template.html` — don't override.

## 1. Core rules — a Twilio workshop, not a customer-application design doc

**Every workshop generated by this skill is scoped to Twilio integration.** The deliverable teaches the customer how to wire specific Twilio products into *their* application — nothing more. It is not a design document for the customer's own systems, business logic, data model, or product surface. Three hard rules — if any downstream guidance feels ambiguous, resolve it against these.

### Rule 1 — Verify, don't paraphrase

Before drafting any journey, Twilio components slide, or implementation step, consult the relevant Twilio product skill (`twilio-voice-conversation-relay`, `twilio-conference-calls`, `twilio-taskrouter-routing`, `twilio-conversation-intelligence`, `twilio-customer-memory`, `twilio-conversation-orchestrator`, `twilio-agent-connect`, etc.) and the Twilio docs MCP (`mcp__twilio-docs__twilio__search` / `mcp__twilio-docs__twilio__retrieve`). Every time, not from memory — product surfaces change. Verify:

- What a Twilio product *is* (role, layer, product vs. SDK) — especially names that collide with generic terms: Conversation Orchestrator, Conversation Memory, Conversation Intelligence, ConversationRelay, Agent Connect, Programmable Messaging, Conversations, Studio, Flex, TaskRouter.
- What a Twilio URL parameter does, when it fires, what payload it receives, what it returns (`action_url`, `statusCallback`, every webhook/callback/connect-verb/studio-widget).
- API shapes, parameter names, event names, endpoint paths.

Product-identity details (TAC, Orchestrator, ConversationRelay, Memory, CI, customer-domain tool bodies) live in **`references/twilio-products.md`** — read it before drafting any journey or implementation step touching those products. For current Twilio API call shapes, open the matching page in **`references/sierra-reference/`** and copy imports, env vars, and call shape verbatim (strip Streamlit UI wrapping).

**This rule applies to every downstream step** — journey drafting, Twilio components slides, Mermaid sequence diagrams, snippet writing. Where other sections say "cross-check against product skills," they mean this rule.

### Rule 2 — No assumptions about the customer's side of the design

The customer's application, business rules, data schema, internal tool bodies, agent-desktop UX, decision engines, and domain-specific workflows are all out of scope for the deck. Reference customer-owned surface only where a Twilio integration boundary touches it (e.g. "the LLM calls the customer's existing `matchPatient` tool" — name it, describe its input/output shape as the boundary contract, but do not fabricate its body or prescribe how it should be built). If the workshop appears to require inventing customer-side design to fill in gaps, **stop and ask the user** — do not extrapolate.

### Rule 3 — Customer-facing output

The deck is shared directly with the customer. Every sentence is read by the customer, not the SA delivering it.

- **No presenter asides.** No "so the customer can see the delta", "helps the customer decide between X and Y", "the workshop treats X as Y", "we're leaving X out because…", "this slide covers…" — meta-commentary about the workshop's own scoping.
- **No disclaimers inside the slide.** No "illustrative pattern", "representative shape", "swap in your real X here", "names are placeholders". If a snippet's specifics matter enough that generated names would confuse the customer, gather the real ones before drafting. Presenter notes go in an internal brief, never in the deck.
- **No third-person "the customer".** Address the reader directly (`you`, `your application`, `your existing systems`) or use neutral phrasing (`the application`, `existing services`). Exception: when "the customer" refers to the *end user* of the built system (a patient, a tax filer), that's fine.
- **No negation-of-alternatives.** The deck states, it doesn't refute. Cut negations — just state the current claim. Exception: factual scoping the reader needs ("this step does not use TAC") is fine.

## 2. Workflow

Follow these steps in order.

1. **Confirm trigger fit.** The frontmatter description lists trigger phrases ("workshop agenda", "workshop HTML", "workshop/hackathon agenda for X"). If the request says "presentation", "PDF", or "PPTX", confirm the user actually wants the HTML workshop deliverable before starting.
2. **Gather inputs** per §3 below. Walk the input list top-to-bottom; ask only for what's missing or can't be inferred.
3. **Run the compliance check** (see §3) if the use case is HIPAA- or PCI-regulated. Do this before scoping journeys — eligibility affects which products you can tag.
4. **Verify every Twilio product tagged in any journey** per Rule 1 — product skills + docs MCP + `references/twilio-products.md` + `references/sierra-reference/`.
5. **For every snippet you plan to use, check `snippets/{language}/README.md` first.** If a match exists, copy that file into the code panel verbatim (or with the minimal customer-specific diff). Only write a new snippet when nothing in the index matches. (Pre-flight the whole deck's snippet needs now so you only read each file once.)
6. **Copy `templates/agenda-template.html`** and fill in placeholders slide-by-slide, following §4 structure.
7. **If a build log was requested**, duplicate `templates/implementation-slide-tabbed.html` (two slides per journey — Overview + Steps) once per journey and insert after Outcomes, in the same order as the journey slides. Bonus journeys last. Follow `references/implementation-slides.md`.
8. **If a Twilio components slide was requested** (sometimes asked for as an "architecture diagram" — but the slide is named "Twilio components" to disambiguate from the customer's own system-architecture work), copy `templates/twilio-components-slide.html` into the deck between Prerequisites and Journeys, then read `references/twilio-components-slide.md` — it has the mandatory numeric verification gate for any part of the hand-rolled SVG you change.
9. **Run the final-pass checklist** (§5) before saving.
10. **Save as `workshop-agenda-{customer-slug}.html`.** After generating a build log with new snippets, ask the user whether to save new/reusable ones into `snippets/{language}/`.
11. **Offer PDF export.** Once the user confirms the HTML looks right, offer to convert it to a PDF for sending to the customer (see the `pdf` skill).

## 3. Inputs to gather

For every item: if the user names it, use it; if a short placeholder can be auto-generated from context, do so; otherwise ask. If the user gives partial information, generate what you can and ask a single follow-up for the rest.

1. **Compliance regime** — HIPAA, PCI, both, or neither. **[required — ask first]** It affects prereqs and product eligibility.
2. **Workshop length** — 1–3 days, dates. **[required]**
3. **Workshop/customer name** — **[required]** if given, use it; otherwise auto-generate from the use case (e.g. "Patient Handler PoC").
4. **In-person, virtual, or hybrid** — **[required]** ask before location. If in-person or hybrid, ask for the customer's location and include it in the header meta. If fully virtual, don't include a location.
5. **Tech stack** — Python or TypeScript. **[required]** Don't assume. TAC has SDKs for both (`tac` on PyPI, `twilio-agent-connect` on npm) with different shapes — see `references/twilio-products.md`.
6. **Journeys** — **[required]** use cases in build order, which Twilio products each touches. Short titles: use the user's or auto-generate. Ask once per journey whether it's committed or **bonus**.
7. **Agenda only, or agenda + implementation build log?** **[required]** If build log: for each journey, ask what was actually built — steps, snippets, screenshots worth preserving. Never invent plausible "what we built" content.
8. **Engagement framing** — **[ask only if ambiguous]** kicks off or continues a longer engagement? Any prior work to recap?
9. **Meals / social event** — **[ask only if applicable]** only include if confirmed.

### Compliance check (HIPAA / PCI)

If the customer or use case is HIPAA- or PCI-regulated, verify per Rule 1 — every time, not from memory. Eligibility changes.

- **HIPAA:** use the sibling skill `twilio-security-compliance-hipaa`.
- **PCI:** do a focused `mcp__twilio-docs__twilio__search` with `"[product name]" PCI compliant site:twilio.com`.
- A changelog post announcing new eligibility overrides an older/general docs page.
- If a product isn't eligible for the regime in scope, don't silently drop or swap it — **flag it directly**, name the product, state what it's not eligible for, and ask how to proceed.
- If Twilio sources conflict, surface that to the user.
- The compliance posture appears as a short tail on the cover subtitle (e.g. `"…same dialog, same tools, new runtime. HIPAA compliant."`) — not as a prerequisite list item.

## 4. Slide structure

One slide per screen, in this fixed order. The template auto-counts via `document.querySelectorAll('.slide')` — just make sure every slide is a `<section class="slide">` with its own `data-menu` and `data-menu-group`.

| # | Slide | Count | Eyebrow |
|---|---|---|---|
| 1 | Cover | 1 | — |
| 2 | Prerequisites | 1 | 01 |
| 3 | Twilio components (optional) | 0 or 1 | 02 if present |
| 4 | Journeys | **1 per journey** | 02 (or 03) |
| 5 | Agenda · Day N | 1 per day | 03 (or 04) |
| 6 | Outcomes | 1 | 04 (or 05) |
| 7 | Implementation (optional) | **2 per journey** (Overview + Steps) | 05 (or 06) |

**Eyebrow numbering shifts by one when the Twilio components slide is present.** Keep the eyebrow consistent across both slides of an Implementation pair.

### 4.1 Cover

Title, bespoke subtitle (grounded in this customer's project; never boilerplate), meta row (Duration, Dates, Stack always; Location only if in-person/hybrid). If HIPAA- or PCI-regulated, append a one- or two-word compliance tail to the subtitle.

### 4.2 Prerequisites (01)

Plain list, no checkboxes. Default items:

| Condition | Prereq | Notes |
|---|---|---|
| Voice/ConversationRelay/CINTEL in scope | **Twilio account** with voice-capable number, PCI mode disabled | Link account setup docs |
| Workshop in India (or any region where numbers can't be purchased) | Drop the number provisioning language; **ask the user how they want to handle testing** | Options to offer: (a) a pre-provisioned number from another region, (b) **Twilio Dev Phone** — a browser-based endpoint for sending/receiving voice + SMS without provisioning a Twilio number (requires the Twilio CLI: `twilio plugins:install @twilio-labs/plugin-dev-phone` then `twilio dev-phone`; link [Dev Phone docs](https://www.twilio.com/docs/labs/dev-phone) and [Twilio CLI install](https://www.twilio.com/docs/twilio-cli/getting-started/install)), or (c) something the customer already has set up. Only add the chosen option as a prereq — do not list Dev Phone or the CLI by default. |
| TAC used | **Twilio Agent Connect** | Describe as "a Python SDK that acts as middleware between your LLM application and Twilio's voice + messaging services." Link [Agent Connect docs](https://www.twilio.com/docs/conversations/agent-connect) and [Quickstart](https://www.twilio.com/docs/conversations/agent-connect/quickstart). Say "install and populate the environment variables before Day 1." |
| Local webhook development in scope | **Tunneling tool** (ngrok or equivalent) | — |
| Customer-named systems/credentials | Named inline | — |

**Every prereq that references a Twilio product with its own setup guide should link that guide.** Use `<a target="_blank" rel="noopener">`, one link per doc; if a product has both a landing page and a quickstart, link both. Do NOT paraphrase setup steps beyond the one canonical CLI or `pip install` command — the guide drifts.

Do NOT default to generic developer-environment boilerplate. Do NOT list repo access as a hard requirement. Do NOT list HIPAA project / BAA status or PCI edition as a prerequisite — that belongs on the cover subtitle.

### 4.3 Twilio components (optional)

Only on explicit user request. The user may ask for an "architecture diagram" — clarify that this slide shows the *Twilio components* the workshop will wire together (Conversation Orchestrator + Memory + Intelligence + ConversationRelay), **not** the customer's own system architecture. If the customer needs their own architecture laid out, that's its own slide (or a separate deliverable) and typically built *during* the workshop.

**Copy `templates/twilio-components-slide.html` into the deck** as the starting point — it's the canonical Paper-style diagram with placeholders for the few customer-specific pieces. Then read **`references/twilio-components-slide.md`** for the visual-style rules, layout coordinates, numeric verification gate, and worked examples. Re-run the numeric gate only on the parts you change (e.g. dropping a channel chip).

### 4.4 Journeys — one slide per journey

**Always one journey per slide**, even when they'd fit together. Each journey (including bonus) is its own `<section class="slide">` with its own `h2`, journey-steps list, and tag row.

Description style:

- **Focus on the work, not customer state.** Open directly on the technical work. Cut framing like "the customer is starting to move parts of the voice agent into deterministic logic" — motivation and org context belong in an internal brief.
- **Describe what's being built, not what's being avoided.** No meta-commentary about the architecture choice ("no new orchestration layer", "the LLM stays in charge"). If the right approach is a single tool call, say that plainly.
- Keep every substantive technical point the user provided.
- Do not add mechanics, patterns, or details the user didn't state. If the user said "warm transfer would be valuable," the description says that — not a paragraph on how the bridge works.
- Rework the user's wording into paragraph prose + the required `<ol class="journey-steps">` for the caller flow. Use the customer's own technical nouns in `<code>` tokens.
- Ordering: opening paragraph (what the journey introduces/proves) → numbered caller flow → paragraphs for what's being tested, media strategy, examples → tag row.

**Caller flow format.** Do not compress into an arrow-list of nouns (`intent → intake → match`). Render each step as a natural-language clause inside `<ol class="journey-steps">`:

> 1. Caller calls in.
> 2. Agent determines the reason for the call.
> 3. Agent captures the configured intake details (symptoms, medications, personal details, scheduling preferences).
> 4. Agent repeats key information back for confirmation.
> 5. Agent matches the patient.
> 6. Agent searches appointment availability.
> 7. Agent schedules or reschedules the appointment.
> 8. Agent confirms details back to the caller.

**Bonus journeys.** If the user describes a stretch case ("warm transfer would be valuable but secondary"), add it as its own journey slide with `<span class="tag">Bonus</span>` in the tag row. Bonus journeys **do not get build blocks in the agenda** — they run on leftover build time. But they **do get full implementation slides** (Overview + Steps), so the customer can see what building it would look like.

### 4.5 Agenda — one slide per day

Read **`references/agenda-rules.md`** for block types, required structure, timing rules (lunch at ~3.5h, no mid-morning break, 1.5h session cap), build-block coverage check, and in-person/virtual/hybrid variants.

### 4.6 Outcomes

One concrete, demoable outcome statement per day.

### 4.7 Implementation (optional) — two slides per journey

Read **`references/implementation-slides.md`** for the Overview/Steps structure, what counts as an impl step, code-panel rules, screenshot-panel rules, and the phone-number-provisioning → Console-screenshot pairing rule.

### 4.8 Architecture qualification — don't invent what Twilio already provides

Before writing any journey description or implementation step, read `references/twilio-products.md` (and verify per Rule 1). Core rule:

**Do not invent orchestration layers for behaviors the product provides natively.** No custom "controller", "middleware", "state machine", "orchestrator", or "runtime" abstraction should appear in a journey or implementation step for capability the tagged product already covers. Prefer product configuration + tool calls over new abstractions. If the user describes a flow using framing like "a deterministic X owns Y", read that as an *outcome* (reliable, structured, auditable capture of Y) — then check whether the product already delivers that outcome via configuration.

**Recommend the best-fit model/provider/voice as an impl step.** For products with configurable choices that materially affect the journey (ConversationRelay's `transcriptionProvider` / `speechModel` / `ttsProvider` / `voice`, Conversation Intelligence operators, Verify channels), consult docs to identify which options fit — don't default to out-of-the-box without checking. Add a dedicated impl step early in the journey showing the specific configuration (typically the TwiML verb or REST payload). Cite settings from Twilio's docs; don't guess at option names. If the customer has preferences (licensed ElevenLabs voice, existing Google STT contract), use those — but still show the config explicitly.

Native behaviors that must NOT be re-wrapped, Twilio-native data-shipping mechanisms, and the "customer-domain tool bodies aren't part of a Twilio workshop" rule all live in **`references/twilio-products.md`** — read it before drafting.

If the user's described flow *does* genuinely need a new layer (bespoke orchestrator across multiple channels, logic the tagged products don't cover), name it plainly and justify why native surface isn't enough — surface the choice to the user before drafting.

### 4.9 Sequence diagrams — use Mermaid, not hand-written SVG

Whenever a slide shows a runtime call graph — "when the user does X, these APIs fire in this order with these bodies" — author it as a **Mermaid `sequenceDiagram`** block. Do not hand-write SVG. The browser lays out the diagram deterministically from the text source.

**Setup.** Copy the `<script type="module">` block from `templates/mermaid-setup.html` and paste near the bottom of `<body>`, after the deck-navigation `</script>`. Include exactly once per deck. Do not change the theme variables per deck or use `%%{init: {…}}%%` directives inside individual diagrams. Keep at `mermaid@11`.

**Slide markup:**

```html
<div class="diagram-panel" style="padding: 24px 32px;">
  <div class="diagram-label">POST /some/endpoint · sequence</div>
  <pre class="mermaid" style="background: transparent; margin: 0; text-align: center;">
sequenceDiagram
  autonumber
  actor U as User
  participant App as Orchestrator
  ...
  </pre>
  <p class="diagram-caption">One-sentence takeaway.</p>
</div>
```

**Content rules.**
- **Actors vs. participants.** `actor X as Label` for humans/handsets that light up in the real world (User, Tech phone). `participant X as Label` for services and internal components.
- **Message labels.** Imperative + endpoint: `POST /Stores/{store}/Profiles`. JSON body / key parameters on a second line with `<br/>`.
- **Notes between calls.** `Note over App: what it's doing<br/>on a second line if needed`.
- **Conditional branches.** `alt <guard>` / `end`; nest naturally.
- Verify APIs and parameters per Rule 1.

### 4.10 General rules on subtext and descriptions

Every `.t-desc`, `.t-note`, `.step-desc`, and `.section-sub` must convey information the reader doesn't already have from the title. If a line just restates the title in different words, cut it.

### 4.11 Navigation menu

Every deck ships a left-hand collapsible slide menu, listing every slide by `data-menu` and grouped under section headings from `data-menu-group`.

- `data-menu-group="Overview"` on Cover + Prerequisites
- `data-menu-group="Twilio components"` on the Twilio components slide (if present)
- `data-menu-group="Journeys"` on each journey slide
- `data-menu-group="Agenda"` on each per-day agenda slide
- `data-menu-group="Outcomes"` on the outcomes slide
- `data-menu-group="Implementation"` on every Overview/Steps slide

Short `data-menu` values scoped to their group: `"Cover"`, `"Prerequisites"`, `"Journey 1 — Intake & Scheduling"`, `"Day 1"`, `"Outcomes"`, `"Journey 1 · Overview"`, `"Journey 1 · Steps"`, `"Bonus · Overview"`, `"Bonus · Steps"`. **Spell out "Journey N" — do not abbreviate to `"J1"`.**

Tabs within an implementation slide are a separate, local interaction (scoped per `.slide-inner`) and never trigger slide navigation.

## 5. Final-pass checklist

Structural and grep-level checks before saving. Content rules are in §1 and §4 — this list only catches regressions.

**Grep for always-wrong phrases:**
- [ ] `illustrative`, `representative`, `placeholder`, `swap in`, `the workshop treats`, `we chose`, `we're`, `so the customer`, `for the customer` → cut or rewrite.
- [ ] Negation fragments: `is not`, `isn't`, `is neither`, `not itself`, `rather than a`, `as opposed to`, `— not `, `, not `. Each hit needs intent (factual scoping is fine; corrective negation is not).

**Slide structure:**
- [ ] Slide count: cover + prereqs + (0 or 1 arch) + N journeys + D days + outcomes + (0 or 2N impl).
- [ ] Every `<section class="slide">` has both `data-menu` and `data-menu-group`.
- [ ] Eyebrow numbers consistent — if Twilio components slide is present, every slide after it shifts by one; both slides of an Implementation pair share the same eyebrow.
- [ ] Journeys = one slide per journey (not stacked).
- [ ] Each Implementation Overview's `<ol class="impl-recap">` `<strong>` labels match the Steps slide's `.impl-tab-btn` text exactly.

**Snippets:**
- [ ] Every impl step either has a `.code-panel`, has a `.screenshot-panel` and is a documented exception, or is a documented customer-owned-code step.
- [ ] Every snippet's non-standard identifiers are introduced at the top (imports, types).
- [ ] No fabricated Twilio surface (`controllerRegistry.*`, `existingAgentRuntime.*`) and no `@customer/*` import where a Twilio-native mechanism exists.

**Final file:**
- [ ] Only the Google Fonts `<link>` is external; everything else is inline (CSS, JS, base64 images).
- [ ] Saved as `workshop-agenda-{customer-slug}.html`.

## 6. Reference files

This skill is modular — new products, languages, and customer engagements should each just add a file, not require editing existing ones.

**Templates (copy-and-fill):**
- `templates/agenda-template.html` — base deck shell (CSS, JS, slide structure) with `{{PLACEHOLDER}}` tokens. Always start from this file. Theme, print, and navigation JS live here; don't override.
- `templates/implementation-slide-tabbed.html` — Overview + Steps partials for one journey. Duplicate per journey when a build log is included.
- `templates/twilio-components-slide.html` — the canonical Paper-style Twilio components slide. Drop in between Prerequisites and Journeys only on explicit user request.
- `templates/mermaid-setup.html` — Mermaid initializer (ESM from jsDelivr, `mermaid@11`) with the Paper palette baked into `themeVariables`. Drop once per deck.

**References (read on demand):**
- `references/twilio-products.md` — product identity (TAC, Orchestrator, ConversationRelay, Memory, CI), native behaviors that must not be re-wrapped, Twilio-native data-shipping mechanisms, and the customer-domain tool-body rule. Read before drafting any journey or implementation step.
- `references/twilio-components-slide.md` — visual-style rules, layout coordinates, numeric verification gate for the hand-rolled SVG, and worked examples. Read before drafting a Twilio components slide.
- `references/agenda-rules.md` — block types, required structure, timing rules, build-block coverage, in-person/virtual/hybrid variants. Read before drafting the Agenda slides.
- `references/implementation-slides.md` — Overview/Steps structure, impl-step shape rules, code-panel and screenshot-panel rules, phone-provisioning → Console-screenshot pairing. Read before drafting an Implementation pair.
- `references/sierra-reference/` — vendored copies of the SAA team's internal "Twilio API Explorer" (`pages/*.py`). Canonical reference for current Twilio API call shapes. See its `README.md` for the file-to-product mapping and the strip-Streamlit rule.

**Snippets (reusable code):**
- `snippets/{language}/` — reusable code snippets, one file per product/pattern, named `{product}-{action}.{ext}` (lowercase-kebab). **Each language directory has a `README.md` index** listing every snippet by product + action with its symbols/endpoints. Before writing a snippet, read that README; if a match exists, copy the file into the code panel verbatim.

**Assets:**
- `assets/console/` — reusable, customer-agnostic screenshots (e.g. "where the Voice URL field lives in Console"). Customer-specific screenshots do NOT go here.
