# Twilio Workshop Agenda Generator

Produces a single self-contained HTML file for a technical workshop/hackathon agenda, presented as a **paginated slide deck** — one full-viewport section per screen, Next/Prev buttons plus arrow-key navigation, a dot indicator, a slide counter, and a collapsible left-hand slide menu (open by default). Each click/keypress transitions to a new "page" (fade + slight vertical shift).

**Navigation is buttons and arrow keys only.** Do not implement scroll-to-advance / wheel-driven page transitions — this was tried and reverted; it fights with the native in-slide scrolling long slides need and feels broken. A slide that overflows its viewport scrolls internally via plain `overflow-y: auto` — that's the only scroll behavior in the deck.

Visual identity is **"Paper"** — warm cream background, Fraunces serif headings paired with IBM Plex Sans body text and IBM Plex Mono for timestamps/labels/code, a dotted timeline, and a tilted stamp-style section label (`.eyebrow`). Color-coded session types: talk = dusty blue, build = terracotta (primary accent), planning = ochre, retro = violet. No decorative chrome beyond that.

## Scope — a Twilio workshop, not a customer-application design doc

**Every workshop generated by this skill is scoped to Twilio integration.** The deliverable teaches the customer how to wire specific Twilio products into *their* application — nothing more. It is not a design document for the customer's own systems, business logic, data model, or product surface. Two hard rules:

1. **Verify, don't paraphrase — consult Twilio skills and MCP before drafting any journey, architecture slide, or implementation step.** For every product tagged in a journey, look up its current shape via the corresponding Twilio product skill (`twilio-voice-conversation-relay`, `twilio-conference-calls`, `twilio-taskrouter-routing`, `twilio-conversation-intelligence`, `twilio-customer-memory`, `twilio-conversation-orchestrator`, `twilio-agent-connect`, etc.) and the Twilio docs MCP (`mcp__twilio-docs__twilio__search` / `mcp__twilio-docs__twilio__retrieve`). Do this every time, not from memory — product surfaces change. This verification requirement applies to:
   - What a Twilio product *is* (role, layer, product vs. SDK vs. role) — especially products whose names collide with generic terms (Conversation Orchestrator, Conversation Memory, Conversation Intelligence, ConversationRelay, Agent Connect, Programmable Messaging, Conversations, Studio, Flex, TaskRouter).
   - What a Twilio URL parameter does, when it fires, what payload it receives, what it returns (`action_url`, `statusCallback`, every webhook/callback/connect verb/studio widget). The specific recurring failure: writing "the `action_url` is the endpoint that returns TwiML…" from memory — it's actually a *post-session callback*, Twilio POSTs to it *after* the verb ends.
   - API shapes, parameter names, event names, endpoint paths.

2. **Make no assumptions about the customer's side of the design.** The customer's application, business rules, data schema, internal tool bodies, agent-desktop UX, decision engines, and domain-specific workflows are all out of scope for the deck. Reference customer-owned surface only where a Twilio integration boundary touches it (e.g. "the LLM calls the customer's existing `matchPatient` tool" — name it, describe its input/output shape as the boundary contract, but do not fabricate its body or prescribe how it should be built). If the workshop appears to require inventing customer-side design to fill in gaps, stop and ask the user — do not extrapolate.

These two rules are load-bearing for everything below. When any downstream rule feels ambiguous, resolve it against these two principles.

## Customer-facing output rule

**The deck is shared directly with the customer.** Every sentence is read by the customer, not by the SA or presenter delivering it. Consequences:

- **No presenter asides.** No "so the customer can see the delta", "for the customer to compare against", "helps the customer decide between X and Y", "the workshop treats X as Y", "we're leaving X out because…", "this slide covers…" — meta-commentary about what the reader is meant to learn, or about the workshop's own scoping.
- **No disclaimers inside the slide.** No "illustrative pattern", "representative shape", "swap in your real X here", "names are placeholders", "representative — swap in the customer's real X during the build". If a snippet's specifics matter enough that generated names would confuse the customer, gather the real ones before drafting — don't paper over it with an in-slide disclaimer. Presenter notes go in an internal brief, never in the deck.
- **No third-person "the customer".** Don't write "the app the customer builds", "the customer's existing systems by name", "tools the customer owns". Address the reader directly (`you`, `your application`, `your existing systems`) or use neutral phrasing (`the application`, `existing services`). Exception: when "the customer" refers to the *end user* of the built system (a patient, a tax filer, an account holder), that's fine.
- **No negation-of-alternatives.** The deck states, it doesn't refute. When you find yourself writing "X is not Y" — even when Y is a common misconception — cut the negation and just state X. "TAC is a Python SDK … not a box on this diagram" → "TAC is a Python SDK." "Conversation Orchestrator is a Twilio product, not the app you build" → "Conversation Orchestrator is a Twilio product that captures traffic across channels." The negation half is a correction directed at the author's own past mistake, not information the reader needs. Exception: factual scoping the reader needs ("this step does not use TAC") is fine.

**Words to grep for and challenge in every generated deck:** `the customer`, `for the customer`, `so the customer`, `the workshop treats`, `we're`, `we chose`, `illustrative`, `representative`, `placeholder`, `swap in`, `so you can see`, `is not`, `isn't`, `is neither`, `not itself`, `not a`, `not the`, `rather than a`, `as opposed to`, `— not `, `, not `. Not every hit is wrong (end-user mentions, idiom like "warm-transferred", genuine scoping) — every hit needs a second look.

**Why this matters.** These rules live in the skill, not the deck, precisely because past decks had presenter asides and corrective negations slip in. Guard against those mistakes in authoring; the customer sees only the current, correct claim.

## Reference files

This skill is modular — new products, languages, and customer engagements should each just add a file, not require editing existing ones.

- `templates/agenda-template.html` — the base deck shell (CSS, JS, slide structure) with `{{PLACEHOLDER}}` tokens and structural comments, covering the cover, prerequisites, journeys, per-day agenda, and outcomes slides, plus the shared nav bar and collapsible left-hand slide menu. Always start from this file.
- `templates/implementation-slide-tabbed.html` — a single-journey implementation slide partial. Duplicate per journey when a build log is included.
- `templates/mermaid-setup.html` — the Mermaid initializer (ESM from jsDelivr, pinned to `mermaid@11`) with the Paper palette baked into `themeVariables`. Drop the `<script type="module">` block once per deck, near the bottom of `<body>`. Every `<pre class="mermaid">` block picks up the theme automatically. **Do not hand-write SVG for sequence diagrams — Mermaid owns layout.** See "Sequence diagrams" below.
- `references/architecture-slide.md` — **read this before drafting an Architecture slide.** Contains the visual-style rules, layout coordinates, numeric verification gate for the hand-rolled SVG, and worked examples. The Architecture slide is optional and only drawn on explicit request.
- `snippets/{language}/` — reusable code snippets, one file per product/pattern, named `{product}-{action}.{ext}` (lowercase-kebab), not after the customer. **Each language directory has a `README.md` index** listing every snippet by product + action with its symbols/endpoints — the model's lookup table. Before writing a snippet for an implementation step, read that README; if a match exists, copy the file into the code panel verbatim (or with the minimal diff needed). Only write a new snippet when nothing in the index matches. After generating a build log with new snippets, ask the user whether to save them to the library and add a one-line README entry.
- `assets/console/` — reusable, customer-agnostic screenshots (e.g. "where the Voice URL field lives in Console"). Customer-specific screenshots do NOT go here — see Screenshots below.
- `/Users/dnaidu/projects/sierra-test/` — the canonical **Twilio API reference repo** (a Streamlit "Twilio API Explorer" the SAA team maintains). Its `pages/` directory covers the real, current API shapes for the products this skill's workshops target — ConversationRelay (`conversation_relay.py`), TAC outbound Voice + SMS (`actions.py`), Conversations (`conversations.py`, `channels.py`), Conversation Intelligence + Memory (`ci_memory.py`), Voice Insights / CR observability (`cr_insights.py`), TaskRouter / Flex (`flex_sdk.py`). Before writing any snippet that touches one of these products, open the relevant sierra-test page and copy its imports, environment variables, and call shape. Strip the Streamlit UI wrapping (`st.*` calls) and the `record_request` / `inspector` instrumentation, but keep the underlying Twilio calls verbatim. Do NOT invent Twilio surface that isn't in sierra-test.

## Inputs to gather before generating

Walk this list top-to-bottom; ask for whatever's missing. **Rule for every item:** if the user names it, use it; if a short placeholder can be auto-generated from context (customer name, journey titles), do so — don't ask; otherwise ask. If the user gives partial information, generate what you can and ask a single follow-up for the rest.

1. **Compliance regime** — HIPAA (healthcare/PHI), PCI (payments), both, or neither? Check this first because it affects prereqs and product eligibility. See **Compliance check** below.
2. **Workshop length** — 1–3 days, dates.
3. **Workshop/customer name** — if given, use it; otherwise auto-generate from the use case (e.g. "Patient Handler PoC").
4. **In-person, virtual, or hybrid** — ask before location. If in-person or hybrid, ask for the customer's location and use it in the header meta. If fully virtual, don't ask for or include a location.
5. **Tech stack** — e.g. Python or TypeScript — don't assume one. TAC has official SDKs for both: `tac` on PyPI (Python) and `twilio-agent-connect` on npm (TypeScript, `github.com/twilio/twilio-agent-connect-typescript`). The Python surface is what sierra-test uses; the TypeScript surface is slightly different (`TAC.create()` is async, `TACServer` registers routes, `twimlOptions.welcomeGreeting` on voice). Pick the SDK that matches the customer's stack and cross-check against the appropriate example repo before drafting — do not paraphrase the API from the other language's shape.
6. **Agenda only, or agenda + implementation build log?** If build log: for each journey, ask what was actually built (or planned) — the steps, snippets, screenshots worth preserving. Never invent plausible-looking "what we built" content.
7. **Engagement framing** — does this workshop kick off or continue a longer engagement? Any prior work to recap, or greenfield?
8. **Journeys** — the use cases to be built, in build order, and which Twilio products each touches. Journey short titles: if the user gives one, use it; otherwise auto-generate. Ask once per journey whether it's committed or **bonus** (see Journeys below).
9. **Meals / social event** — only include if confirmed.

## Compliance check (HIPAA / PCI)

If the customer or use case is HIPAA- or PCI-regulated, do this before finalizing the journeys/prerequisites — every time, not from memory:

1. For each named Twilio product in the journeys, web-search Twilio's own docs for its current eligible status — search terms like `"[product name]" HIPAA eligible site:twilio.com` and `"[product name]" PCI compliant site:twilio.com`. A changelog post announcing new eligibility overrides an older/general docs page.
2. Eligibility changes over time — never assume from a prior conversation or general knowledge.
3. If a product isn't eligible for the regime in scope, don't silently drop or swap it — flag it directly, name the product, state what it's not eligible for, and ask how to proceed.
4. If Twilio's sources conflict, surface that to the user.
5. The compliance posture appears as a short tail on the cover subtitle (`"…same dialog, same tools, new runtime. HIPAA compliant."`) — not as a prerequisite list item.

## Slide structure

One slide per screen, in this fixed order:
1. **Cover** — title, bespoke subtitle (grounded in this customer's project; never boilerplate), meta row (location only if in-person/hybrid). If HIPAA- or PCI-regulated, append a one- or two-word compliance tail to the subtitle.
2. **Prerequisites** (01) — plain list, no checkboxes. See prereq rules below.
3. **Architecture** (optional, 02 if present) — only on explicit user request. Read `references/architecture-slide.md` before drafting. When present, shifts the eyebrow numbering of every slide after it.
4. **Use cases & journeys** (02 or 03) — **one slide per journey**, including bonus journeys. See Journeys section below.
5. **Agenda · Day N** — one slide *per day*. Don't cram multiple days onto one slide.
6. **Outcomes per day** — one slide, all days' outcomes together.
7. **Implementation** (optional) — **two slides per journey** (Overview + Steps), appearing after Outcomes, in the same order as the journey slides. Bonus journeys get the same two-slide treatment and appear last.

**Slide count** = cover + prereqs + optional Architecture + N journeys + D days + outcomes + (0 or 2N implementation). The template auto-counts via `document.querySelectorAll('.slide')`, so no manual edits — just make sure every slide is a `<section class="slide">` with its own `data-menu`.

### How in-person vs. virtual changes the agenda

- **In-person**: include an arrival buffer before the formal start; a location field in the header meta; an optional evening social block if confirmed, with a `t-note` only if the venue is genuinely TBD.
- **Virtual**: no location, no arrival buffer, no dinner block; keep breaks shorter and more frequent. Don't invent a "join link" placeholder.
- **Hybrid**: ask for location (for the in-person side); note which sessions are in-person-only.

## Prerequisites — content rules

Plain list, no checkboxes. Default items:

- **Twilio account** (voice-capable number provisioned) with **PCI mode disabled on the account** — only if Voice/ConversationRelay/CINTEL is in scope.
  - **India exception:** Twilio does not currently sell numbers in India. When the workshop is in India (or any region where numbers can't be purchased), drop the number provisioning language and add the Twilio Dev Phone prereq. Confirm the region with the user before deciding.
- **Twilio Dev Phone** — required whenever the account can't provision a physical number (India today, or any other constrained region). Describe as "a local development tool that gives you a browser-based endpoint for sending and receiving voice + SMS without provisioning a Twilio number." Include CLI install: `twilio plugins:install @twilio-labs/plugin-dev-phone` then `twilio dev-phone`. Link both the [Dev Phone docs](https://www.twilio.com/docs/labs/dev-phone) and the [Twilio CLI install guide](https://www.twilio.com/docs/twilio-cli/getting-started/install).
- **Twilio Agent Connect (TAC)** — required when TAC is used. Describe as "a Python SDK that acts as middleware between your LLM application and Twilio's voice + messaging services." Link the [Agent Connect docs](https://www.twilio.com/docs/conversations/agent-connect) and the [Quickstart](https://www.twilio.com/docs/conversations/agent-connect/quickstart). Say "install and populate the environment variables before Day 1" so attendees don't burn workshop time on setup.
- A **tunneling tool** (ngrok or equivalent) — only if local webhook development is in scope.
- Any customer-specific systems or credentials the user names.

**Every prereq that references a Twilio product with its own setup guide should link that guide.** Use anchor tags with `target="_blank" rel="noopener"`, one link per doc; if a product has both a landing page and a quickstart, link both. Do NOT paraphrase setup steps beyond the one canonical CLI or `pip install` command — the guide drifts.

The deck's global stylesheet needs a themed link style: `.p-desc a, .lede a, .arch-recap a { color: var(--terracotta); text-decoration: none; border-bottom: 1px solid rgba(181,80,46,0.35); } .p-desc a:hover, .lede a:hover, .arch-recap a:hover { border-bottom-color: var(--terracotta); }`.

Do NOT default to generic developer-environment boilerplate. Do NOT list repo access as a hard requirement. Do NOT list HIPAA project / BAA status or PCI edition as a prerequisite — that posture belongs on the cover subtitle.

## Journeys — content rules

**One journey per slide**, always — do not stack multiple journeys onto a single slide, even when they'd fit. Each journey (including bonus journeys) gets its own `<section class="slide">`, sharing the eyebrow but with its own `h2`, flow list, and tag row. This keeps every journey full-viewport-legible.

**How to write the journey description:**

- **Focus on the work, not customer state.** The description is about what will be built or proven in this journey, not what the customer is "starting to explore" or "moving toward." Cut framing like "the customer is starting to move parts of the voice agent into deterministic logic" — open directly on the technical work. Motivation and organizational context belong in an internal brief.
- **Describe what's being built, not what's being avoided.** No meta-commentary about the architecture choice ("no new orchestration layer", "the LLM stays in charge", "keeps ownership of X"). If the right approach is a single tool call, say that plainly. The road not taken belongs in a talk track, not on the slide.
- Keep every substantive technical point the user provided. Losing substance is an omission.
- Do not add mechanics, patterns, or details the user didn't state. If the user said "warm transfer would be valuable," the description says that — not a paragraph on how the bridge works.
- Rework their wording into paragraph prose + the required `<ol class="journey-steps">` for the caller flow. Break secondary points into their own short paragraphs after the flow list, using the customer's own technical nouns (`<code>` for tokens like `primaryText` or `play`).
- Ordering: opening paragraph stating *what the journey introduces / proves* → numbered caller flow → paragraphs for what's being tested, media strategy, examples → tag row.

**Caller flow format.** Do not compress into a short arrow-list of nouns (`intent → intake → match → schedule`). Render each step as a natural-language clause inside an `<ol class="journey-steps">`:

> 1. Caller calls in.
> 2. Agent determines the reason for the call.
> 3. Agent captures the configured intake details (symptoms, medications, personal details, scheduling preferences).
> 4. Agent repeats key information back for confirmation.
> 5. Agent matches the patient.
> 6. Agent searches appointment availability.
> 7. Agent schedules or reschedules the appointment.
> 8. Agent confirms details back to the caller.

Add to the deck's inline `<style>` if not already there: `.journey ol.journey-steps { color: var(--text-dim); font-size: 14.5px; margin: 0 0 12px 0; padding-left: 22px; max-width: 560px; } .journey ol.journey-steps li { margin-bottom: 4px; padding-left: 4px; }`.

**Bonus journeys.** If the user describes a "stretch" or "if-time-permits" case ("warm transfer would be valuable but secondary"), add it as its own journey slide with `<span class="tag">Bonus</span>` in the tag row. Bonus journeys **do not get build blocks in the agenda** — they run on leftover build time. But they **do get full implementation slides** (Overview + Steps), so the customer can see what building it would look like. Ask the user once per journey whether it's committed or bonus.

## Agenda — content rules

Per-day timeline with real start/end times:

- Welcome/intros, then a recap block only if there's genuinely prior work.
- Architecture review / scope-setting before building starts.
- **Build blocks mapped 1:1 to the journeys**, tagged `build` (terracotta). Every regular (non-bonus) journey must have real build blocks — not a "scoping" or "walkthrough" planning slot. Timeline titles name what's being built ("Journey N — {step name}"). Before drafting the timeline, list every regular journey and confirm each has at least one build block; if the duration can't fit them all, **flag it to the user and ask what to drop or defer** — do not silently demote a journey to a planning slot. Bonus journeys consume leftover build time.
- A retro (`retro`, violet) at the end of each day; a standup (`talk`, dusty blue) at the start of subsequent days.
- Meals as their own `break`-class rows, no format tag and no invented description.
- **No mid-morning break.** Do not insert a short break ~90 minutes in — go straight through from the day's opening block into the first build block until lunch.
- **Lunch after ~3.5 hours** from the day's start (e.g. 09:00 start → 12:30 lunch). Apply on every day, including Day 2+ where the morning kicks off with a standup.
- **No single session runs longer than 1.5 hours**, by default. Caps build blocks and every other session type. If a stretch of work would run longer, split it into consecutive smaller sessions (even with no break between), each with its own row and descriptive title.
- A closing "what's next"/"ideation" block on the final day, kept generic — never invent a specific hypothetical technical debate.

## Outcomes per day

One concrete, demoable outcome statement per day.

## Implementation slides (section 05)

**Two slides per journey**, back to back:

1. **Overview slide** (`data-menu="Journey {N} · Overview"`, `data-menu-group="Implementation"`) — the recap. Contains the eyebrow `05 — Implementation`, `h2` `"Journey N: {title}"`, the `.tag-row.impl-tags`, and a numbered step-recap `<ol class="impl-recap">` — one `<li>` per implementation step. Each `<li>` leads with the step's number + short name in `<strong>` (matching the tab button label on the next slide exactly), an em dash, and a one-line description reusing the same wording as that step's `.step-title` / `.step-desc`. No tabs, no code — a "what are we about to walk through" preview.
2. **Steps slide** (`data-menu="Journey {N} · Steps"`, `data-menu-group="Implementation"`) — the tabbed detail. Contains the same eyebrow/h2/tag-row and the `.impl-tabs` strip + tab panels described below.

Bonus journeys follow the same pattern with `data-menu="Bonus · Overview"` / `"Bonus · Steps"`.

Splitting overview and tabs is the fixed pattern — the recap list gets long enough that squeezing it above the tabs on a single slide either forces internal scrolling or forces shortening past usefulness.

Every implementation step renders as **a tab**, one tab per step, regardless of count (even a single-step journey uses one tab, for visual consistency).

**Steps slide structure:**
- `.impl-tabs` — one `.impl-tab-btn` per step, labeled `"{step number} {short step name}"` (must match the recap `<li>` `<strong>` labels)
- One `.impl-tab-panel` per tab, each containing:
  - a `.step-title` and `.step-desc` (what was done and why)
  - zero or more `.code-panel` blocks
  - zero or more `.screenshot-panel` blocks

Add to the deck's inline `<style>` if not already there: `ol.impl-recap { color: var(--text-dim); font-size: 14.5px; margin: -4px 0 20px 0; padding-left: 22px; max-width: 720px; } ol.impl-recap li { margin-bottom: 6px; padding-left: 4px; } ol.impl-recap strong { color: var(--text); font-weight: 600; }`.

### What counts as an implementation step

A piece of Twilio-side wiring the workshop actually produces, shown by a code snippet in the tab. Every impl step must contain a `.code-panel` — that snippet is the point. Two named exceptions:

1. **Customer-owned code steps** — body lives in the customer's system; the `.step-desc` alone is the tab (see Code panels rule below).
2. **Console screenshot steps** — the required Twilio Console screenshot tab following any phone-number provisioning / voice-URL configuration step (see "Phone number provisioning" below); the `.screenshot-panel` is the tab.

**Do NOT create impl steps for testing, verification, or edge-case lists.** A `.step-desc` reading "run each of these scenarios" or a code panel that's actually a bulleted test-case checklist is a QA plan, and the deck is not the place for it.

**But do NOT drop the concern either.** Every edge case a journey names — long pauses, filler phrases while the agent is thinking, barge-in/interrupt handling, DTMF fallback, low-confidence STT retries, silence re-prompts — is a real Twilio-side implementation concern with real code (WebSocket message handling for `interrupt` and `dtmf`, filler `text` messages sent while an LLM/tool call runs, silence timers, spell-back turns). Turn each concern into its own single-responsibility impl step with an actual code snippet.

**If you can't figure out the right implementation shape**, ask a targeted question (e.g. "For silence handling — do you want a hard timeout after N seconds, or streaming filler tokens while the LLM runs?") rather than deleting the concern. Consulting the Twilio product skill is the first move; asking is the second; dropping is not an option.

**Impl-step splits are cheap.** A broad concern that would need three distinct snippets becomes three impl steps and three tabs, each with its own single-responsibility snippet.

Workshop time spent exercising scenarios end-to-end against the live number is still a legitimate `build` block on the day agenda — the constraint here is what goes inside the Steps tabs.

### Code panels

- Plain IBM Plex Mono, **no syntax color-coding** — comments/keywords/strings all render the same color. Deliberate choice (matches editorial tone, avoids an extra JS dependency).
- Each panel has a small filename-style label bar (`.code-label`, e.g. `orchestrator-trigger.ts`) matching the workshop's tech stack.
- Before writing a new snippet, **read `snippets/{language}/README.md` first** — it indexes every reusable snippet by product and action. If a match exists, copy that file into the code panel verbatim.
- **All checked-in snippets are trusted.** Treat them as reviewed reference points. Do not rewrite one "to be safe" or "because the shape looks slightly off" — if it's in the folder, it's known-good. Customer-specific tweaks (renamed tool names, different voice/model) are inline edits in the generated deck only; do NOT edit the snippet file to carry them.
- **If a snippet is actually wrong**, fix it in place in `snippets/{language}/{file}` so the next workshop starts from the correction. Do not fork a variant like `foo-v2.{ext}`, do not inline-fix in the deck and leave the file broken — one canonical source per pattern, always.
- After generating a build log with new snippets, **ask the user whether to save the new/reusable ones** into `snippets/{language}/` — if yes, save as `{product}-{action}.{ext}` and add a one-line entry to `README.md`. Don't save silently, don't skip asking.
- Snippets reflect what the user actually tells you was built, or are clearly representative patterns — never fabricate call-outs, endpoints, or config values presented as the customer's real ones. **Never fabricate Twilio framework surface either** (see Architecture qualification below).
- **Snippets are self-contained: every non-standard identifier must be introduced at the top.** A reader looking at the snippet in isolation should see where every referenced symbol comes from — no `agentDesktop.push(...)` or `callStateStore.get(...)` appearing out of thin air. Add a short imports/declares section:
  - `import { X } from '@customer/...'` for customer-owned surface (label so the reader can tell it's their code, not Twilio's).
  - `import { X } from './siblingFile'` for helpers defined in another snippet of the same workshop (reference the exact filename in that snippet's `.code-label`).
  - `import { X } from 'twilio' / 'ws'` etc. for real library imports.
  - `type X = ...` or `interface X { ... }` for types the snippet uses but doesn't define.

  A reader must never have to guess whether a symbol is customer code, Twilio SDK, a Node builtin, or a helper from another slide. If a step doesn't need imports (a pure prompt file, a markdown contract), fine — no imports needed. But no dangling free variables.
- **One responsibility per step; snippets contain only the code implementing that step.** Do not pad with adjacent helpers, "while we're here" utilities, or the opposite side of the current concern (e.g. don't show both `playPrompt` and `speakGlue` in a step titled "deliver stable prompts via `play`"). If related code genuinely needs to be shown, give it its own step and its own tab. Keep snippets minimally sufficient to make the step's wiring reviewable — nothing more.
- **No code snippets for steps whose implementation lives in customer-owned code.** If a step is "call the customer's existing X" or "expose the customer's Y as a tool" — where X or Y lives entirely in the customer's system and Twilio only references it by name — do NOT generate a snippet. The step's `.step-desc` (name of the tool, its input tuple, return shape, where it's called from) is the whole content. A fabricated snippet for customer-owned code adds no reviewable Twilio wiring and risks being read as a spec for their internal system. Snippets are for Twilio-side wiring the workshop actually produces.
- **Function/tool naming**: if the user gives real names, use them. Otherwise, generate structured, well-meaning names from the use case (`matchPatient`, `searchAvailability`, `scheduleAppointment`) — don't ask, don't leave generic stand-ins like `doThing()`. No in-slide disclaimer that names are "representative" or "placeholders" (customer-facing rule).

### Screenshot panels

- Structure mirrors the code panel: bordered `.screenshot-panel` with a caption bar.
- **Always embed images as base64 data URIs** directly in `<img src="data:...">`. Never reference an external file path — the deck stays a single self-contained file (the only external reference is the Google Fonts `<link>`).
- Placement is driven by user instruction — "add this screenshot to step 2 in journey 2" maps to that journey's slide, tab 2's `.impl-tab-panel`.
- Always include a caption. If the user doesn't give one, ask — an uncaptioned screenshot tells a future reader nothing.
- Screenshots usually carry visible SIDs, phone numbers, customer names — flag this once before embedding, but don't attempt automatic redaction.
- Only customer-agnostic, reusable screenshots (e.g. "where to find X in Console") belong in `assets/console/`. Customer-specific screenshots stay embedded in that one workshop's file.

### Phone number provisioning → always follow with a Console screenshot step

## General rule on subtext and descriptions

Every `.t-desc`, `.t-note`, `.step-desc`, and `.section-sub` must convey information the reader doesn't already have from the title. If a line just restates the title in different words, cut it.

## Architecture qualification — don't invent what Twilio already provides

Before writing any journey description or implementation step, for every Twilio product tagged in a journey, consult the corresponding Twilio product skill or docs MCP. This is the "verify, don't paraphrase" rule from Scope, applied to API shapes.

**Do not invent orchestration layers for behaviors the product provides natively.** No custom "controller", "middleware", "state machine", "orchestrator", or "runtime" abstraction should appear in a journey or implementation step for capability the tagged product already covers. Prefer product configuration + tool calls over new abstractions. If the user describes a flow using framing like "a deterministic X owns Y", read that as an *outcome* (reliable, structured, auditable capture of Y), not as a prescription that a new component named X must be built — then check whether the product already delivers that outcome via configuration.

**Recommend the best-fit model / provider / voice, and include it as an impl step.** For every Twilio product with configurable model / provider / voice choices that materially affect the journey's success (ConversationRelay's `transcriptionProvider` / `speechModel` / `ttsProvider` / `voice`, Conversation Intelligence operators, Verify channels), consult the docs / skill to identify which options fit — do not default to the product's out-of-the-box provider without checking. Add a dedicated impl step early in the journey showing the specific configuration (typically the TwiML verb or REST payload), and let the `.step-desc` explain why those choices fit (e.g. "Deepgram `flux` + `partialPrompts` + `deepgramSmartFormat` for structured DOB/phone/name intake with early-turn detection and canonical formatting"). Cite the settings from Twilio's docs; do not guess at option names. If the customer has preferences already (a licensed ElevenLabs voice, an existing Google STT contract), use those — but still show the config explicitly.

### Concrete native behaviors that must NOT be re-wrapped

- **ConversationRelay**: STT/TTS turn management, interruption handling, repeat-back, correction flows, and confirmation loops for structured data (DOB, name, phone, digits) are native to the LLM + relay runtime. Deterministic branching (match / no-match / ambiguous / transfer) belongs in an **LLM tool call** into the customer's existing service — the tool returns a structured outcome and the LLM continues. It does NOT belong in a new "controller" the LLM "hands control to". When a customer says "deterministic patient-matching controller", confirm they mean "the LLM must reliably call our decision engine with clean structured inputs and act on its structured response" before drafting anything that looks like middleware. `play` media messages for stable pre-rendered prompts are also native — use them, don't dress them up as a "media strategy runtime".
- **Conference / warm transfer**: participant management, whisper/coach, hold, and supervisor barge are native — don't write a bespoke "handoff runtime".
- **TaskRouter**: worker/queue/workflow routing, reservations, and skills-based routing are native — don't wrap the API in a custom "router class".
- **Conversation Orchestrator / Memory / Intelligence**: capture, storage, recall, and language operators are native — don't invent a "context service" duplicating what the product already emits.

### When Twilio already ships the data — don't invent a customer dependency

Before writing an `import` from a hypothetical `@customer/{thing}` (agent-desktop, notifier, escalator), stop and ask: does Twilio already ship this data through its own primitives? Common cases where the answer is yes:

| Need | Twilio-native mechanism |
|---|---|
| Handoff context to a human agent on warm transfer | `<Dial><Client><Parameter>` or query-string on `To=client:{id}?callSid=...&reason=...`. Twilio delivers each key as a custom parameter on the incoming call in the agent's Voice SDK. Keep payload under ~800 bytes; send references (SIDs, IDs), not full transcripts. |
| Passing data between call legs / to a TwiML action URL | `<Parameter>` inside `<Dial>`, query-string on the action URL |
| Notifying an external system when call state changes | `statusCallback` and `statusCallbackEvent` on `<Dial>` / `<Conference>` / `<Number>` / `<Client>` |
| Structured routing / skills data | TaskRouter task attributes JSON |
| Media metadata to a WebSocket app | ConversationRelay `customParameters` (via `<Parameter>` children on `<ConversationRelay>`); Media Streams stream parameters |
| Post-call state to an external system | Recording / transcription / Conversation Intelligence webhooks |

Identify the native mechanism, then show two things in the impl step: (1) *what* attributes matter (a typed object naming them), and (2) *how* Twilio ships them (the specific native mechanism, cited from docs). Only reach for a customer-owned import when the target genuinely lives outside Twilio's surface (writing to their own DB or auth system) — and even then, name the surface plainly (e.g. `@customer/patient-directory`).

**Do not fabricate Twilio framework surface in snippets.** Code panels must use real Twilio APIs — for ConversationRelay, actual WebSocket message shapes (`setup`, `prompt`, `interrupt`, `text`, `play`, `end`, tool-call messages) and actual TwiML `<ConversationRelay>` verb parameters; for Conference, real `<Dial><Conference>` verbs and Participants REST endpoints. Do NOT invent methods like `controllerRegistry.attach(...)`, `controller.awaitConfirm(...)`, or `existingAgentRuntime.continueWithToolResult(...)`. If a snippet needs to represent the customer's own system, label it as theirs (a short comment or filename like `customer/decisionEngine.ts`).

If the user's described flow *does* genuinely need a new layer (e.g. a bespoke orchestrator across multiple channels, or logic the tagged products don't cover), name it plainly and justify why the native surface isn't enough — surface the choice to the user before drafting. Don't leave the reader assuming the wrapper is required.

## Twilio product identity — TAC, Orchestrator, ConversationRelay, Memory, Intelligence

These products are frequently confused with each other or with customer-owned code. The verify-against-docs rule applies — do not decide any of this from memory.

### TAC — Twilio Agent Connect (Python helper SDK)

**TAC in the SAA context means Twilio Agent Connect**, the Python helper SDK packaged as the `tac` module. It is NOT "Agent Copilot", not a live-agent desktop, not a Twilio product surface in its own right, and not Conversation Orchestrator. TAC is how a Python customer *integrates with* the Twilio conversational products — it is not a replacement for them.

Refer to the customer's side as "your integration app" or "your application" — never "the Orchestrator" (which is the Twilio product).

The real TAC surface (cross-check `pages/actions.py` in sierra-test before drafting):

- `TAC(config=TACConfig.from_env())` — SDK instance; single per app. Reads `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_PHONE_NUMBER`, `TWILIO_VOICE_PUBLIC_DOMAIN`, and CI/Memory config IDs from env.
- `SMSChannel(tac, config=SMSChannelConfig(memory_mode="always"))` — SMS channel; `memory_mode="always"` enables Twilio Memory hydration on every turn.
- `VoiceChannel(tac, config=VoiceChannelConfig(memory_mode="always"))` — Voice channel with the same Memory hydration.
- `InitiateMessagingConversationOptions(to=..., message=...)` — outbound SMS opts.
- `InitiateVoiceConversationOptions(to=..., websocket_url=..., welcome_greeting=..., action_url=...)` — outbound Voice opts.
  - `websocket_url` is the WebSocket endpoint ConversationRelay connects to for the STT/TTS + LLM turn loop.
  - `action_url` is the **post-session callback** on the `<Connect>` verb. Per the [ConversationRelay docs](https://www.twilio.com/docs/voice/twiml/connect/conversationrelay#connect-action-url-callback), Twilio POSTs to `action_url` *after* the `<Connect>` verb ends, with `SessionStatus` (`ended` / `failed` / `completed`), `HandoffData` (if the app signalled a handoff), and standard call fields (`AccountSid`, `CallSid`, `SessionId`, `SessionDuration`). The TwiML with `<Connect><ConversationRelay>` is generated internally by TAC (or handwritten if going direct) at outbound-call answer time, separate from `action_url`.
- Both channels expose `await channel.initiate_outbound_conversation(opts)`; drive from sync code with `asyncio.run(...)`.

**TAC TypeScript SDK (`twilio-agent-connect` on npm).** Different shape from the Python SDK — cross-check `github.com/twilio/twilio-agent-connect-typescript` before drafting. Core differences:

- `TAC.create({ config: TACConfig.fromEnv() })` is **async** — await the create call.
- `new VoiceChannel(tac)` / `new SMSChannel(tac)` + explicit `tac.registerChannel(channel)`.
- `new TACServer(tac)` + `await server.start()` must run before `initiateOutboundConversation`, so the inbound reply webhook / WebSocket routes exist when the first customer reply lands.
- Voice `initiateOutboundConversation` takes `{ to, twimlOptions: { welcomeGreeting } }` — the greeting lives under `twimlOptions`, not at the top level. Returns `{ callSid }`.
- SMS `initiateOutboundConversation` takes `{ to, message }` and returns `{ conversationId }`.
- Supports additional channels (`RCSChannel`, `WhatsAppChannel`) off the same TAC instance.

Pick the SDK that matches the customer's stack; the two SDKs are not interchangeable in snippet form.

### Conversation Orchestrator (Twilio product, not TAC, not the customer's app)

Per [Twilio docs](https://www.twilio.com/docs/conversations/orchestrator): "the foundational data layer that observes traffic from your Twilio account, links it to customer profiles, and makes it available for AI agents and analytics." A Twilio product — not a role, not an SDK, not "the app the customer builds." If a customer's brief describes an "Orchestrator + Memory + Intel/Intelligence triangle" in their own words, read that as the three Twilio products Conversation Orchestrator + Memory + Intelligence — not license to invent three customer-owned services, and not license to substitute TAC for Conversation Orchestrator.

### ConversationRelay (Voice-only product)

ConversationRelay is Twilio's Voice-specific product — STT/TTS + LLM turn loop + tool calls over a WebSocket. It powers a **single channel (Voice)**. It is NOT the abstraction that manages "Web / SMS / Voice / App" as a set. The reference-image aesthetic that puts SMS/Voice/Web/App icons inside a "CONVERSATION RELAY" box is wrong — cross-channel capture is done by Conversation Orchestrator, not ConversationRelay. On the Architecture diagram, ConversationRelay appears (if at all) as an annotation on the Voice channel.

### Memory and Conversation Intelligence (Twilio products, not customer-owned)

- **Memory** — `https://memory.twilio.com/v1`. TAC hydrates against it via `memory_mode="always"`. Do NOT invent a customer-owned `memory.load()` / `memory.recordOutcome()` / vector-store adapter. If profile or history is needed, the answer is Twilio Memory + `memory_mode`.
- **Conversation Intelligence (CI)** — `https://intelligence.twilio.com/v3`. Custom operators are `POST /Operators`, then attached to a CI config (`TWILIO_CINTEL_ID` env var) via `POST /Services/{cintel_id}/Operators`. Operators run over each transcript to produce intents, summaries, sentiment, redactions. Do NOT invent a custom `analyse()` / "Intelligence layer" that duplicates this.
- **Voice / CR Insights** — `https://insights.twilio.com/v1/Voice/{Summaries,Calls/{callSid}/Events}`. CR-specific event names include `prompt_sent`, `first_token_received`, `final_token_received`, `stt_latency`, `tts_latency`, `start_of_customer_speech`, `end_of_customer_speech`, `start_of_agent_speech`, `end_of_agent_speech`, `configurations`.

### Customer-domain tool bodies are not part of a Twilio workshop

Tool names that clearly belong to the customer's business — `verifyIdentity`, `quoteBalance`, `promiseToPay`, `sendPaymentLink`, `markDNC`, `escalate`, `checkEligibility` — are customer-owned:

- Do NOT invent bodies for these tools; Twilio only references them by name via the LLM's tool-calling surface.
- If a tool is only referenced (e.g. "on `escalateToHuman`, warm-transfer via Flex"), show only the Twilio-side handoff wiring, not the tool body.
- If a tool IS Twilio-side (e.g. `send_link_over_sms` using the Messages API), include a real Twilio snippet.
- If unsure whether a tool is Twilio-side or customer-side, ask before drafting.
- Do not create a dedicated "Agent tools" tab whose body is a fabricated grab-bag of customer domain functions. Either drop the tab (renumber) or narrow it to a single Twilio-native tool with a real snippet.

## Sequence diagrams

Whenever a slide needs to show a runtime call graph — "when the user does X, these APIs fire in this order with these bodies" — author it as a **Mermaid `sequenceDiagram` block**. Do not hand-write SVG. Do not invent an alternative visual language.

**Why Mermaid, not hand-rolled SVG.** Every previous iteration told the model to hand-write `<svg>` with per-element coordinates and verify layout. The model gets that wrong — labels overflow their boxes, arrow origins float in the wrong place, subtitles crop against container edges. Mermaid removes the entire failure mode: the browser lays out the diagram deterministically from the text source. The Paper aesthetic (yellow pills, dashed orange lifelines, gray activation boxes, blue `alt` frames) is preserved via `themeVariables`.

**Proven pattern.** The deck at `/Users/dnaidu/workshops/intuit/chat-identifier-demo-app/jobID_presentation/index.html` uses this setup — Mermaid ESM from jsDelivr, Paper `themeVariables`, `<pre class="mermaid">` blocks inline in slides. Copy that pattern.

**When to reach for a sequence diagram.** Any time you'd otherwise write "the flow is: 1. X calls Y with foo, 2. Y calls Z with bar, 3. …" as prose or a numbered list.

**Installation.**
1. Open `templates/mermaid-setup.html`. Copy the `<script type="module">…</script>` block that imports Mermaid and calls `mermaid.initialize({…})`. Paste near the bottom of `<body>`, after the deck-navigation `</script>`. Include exactly once per deck.
2. Do not change the theme variables per deck.
3. Do not use `%%{init: {…}}%%` directives inside individual diagrams.

**Adding a sequence-diagram slide.** Give the slide its own `data-menu` label and (optionally) `data-menu-group="Sequence diagrams"`. Wrap in `.diagram-panel`:

```html
<div class="diagram-panel" style="padding: 24px 32px;">
  <div class="diagram-label">POST /some/endpoint · sequence</div>
  <pre class="mermaid" style="background: transparent; margin: 0; text-align: center;">
sequenceDiagram
  autonumber
  actor U as User
  participant App as Orchestrator
  ...
  </pre>
  <p class="diagram-caption">One-sentence takeaway.</p>
</div>
```

**Content rules.**
- **Actors vs. participants.** `actor X as Label` for humans/handsets that light up in the real world (User, Tech phone). `participant X as Label` for services and internal components. Choose deliberately.
- **Message labels.** Imperative + endpoint: `POST /Stores/{store}/Profiles`. JSON body / key parameters on a second line with `<br/>`: `POST /v2/Conversations<br/>orchestrator_config_id + participants`. No prose descriptions where the endpoint should go.
- **Notes for logic between calls.** When the app is doing work *between* two calls, add `Note over App: what it's doing<br/>on a second line if needed`.
- **Conditional branches.** Wrap in `alt <guard>` / `end`, e.g. `alt no reusable conversation_id` … `end`. Nested conditionals nest naturally.
- **The message that leaves the system.** The real-world side-effect message (SMS delivered, phone rings, external webhook fires) gets the same signal color — the fact that it's between two `actor`s is visually distinct enough. Do not hand-color.
- **Don't invent APIs or parameters** — cross-check against Twilio product knowledge (see Architecture qualification).

**What NOT to do.** No hand-written `<svg class="uml-sequence">`. No per-block color overrides. No `mermaid@latest` or non-major version — keep at `mermaid@11`. No bare `<pre class="mermaid">` without the `.diagram-panel` wrapper.

## Navigation

Next/Prev circular buttons and dot indicator in a fixed bottom bar; arrow keys (←/→/↑/↓) also navigate. Handled by the shared template script — don't rewrite per agenda. Every slide must be a direct `<section class="slide">` child of `#viewport` so the counter and dots stay in sync. Tabs within an implementation slide are a separate, local interaction (scoped per `.slide-inner`) and never trigger slide navigation.

### Collapsible slide menu (left side)

Every deck ships a left-hand slide menu, listing every slide by name (from each `<section>`'s `data-menu` attribute) and grouped under section headings from `data-menu-group`. Clicking an item jumps to that slide.

**Keep menu labels short** — do not repeat the section number prefix. Set:

- `data-menu-group="Overview"` on Cover + Prerequisites
- `data-menu-group="Journeys"` on each journey slide
- `data-menu-group="Agenda"` on each per-day agenda slide
- `data-menu-group="Outcomes"` on the outcomes slide
- `data-menu-group="Implementation"` on every Overview / Steps slide

Short `data-menu` values scoped to their group: `"Cover"`, `"Prerequisites"`, `"Journey 1 — Intake & Scheduling"`, `"Journey 2 — Patient Matching"`, `"Bonus — Warm transfer"`, `"Day 1"`, `"Day 2"`, `"Outcomes"`, `"Journey 1 · Overview"`, `"Journey 1 · Steps"`, `"Bonus · Overview"`, `"Bonus · Steps"`. **Spell out "Journey N" — do not abbreviate to `"J1"`.** The menu-building script emits an uppercase group divider (`.side-menu-group`) whenever the group changes.

Menu CSS lives inline in the template: `.side-menu-group { font-family: var(--font-m); font-size: 10.5px; letter-spacing: 0.08em; text-transform: uppercase; color: var(--text-faint); padding: 14px 10px 6px 10px; border-top: 1px dotted var(--line); margin-top: 6px; } .side-menu-group:first-of-type { border-top: none; margin-top: 0; padding-top: 4px; }`.

- **Default open.** `<body>` starts with class `menu-open` and `.side-menu` starts with class `open`.
- **Push, not overlay, on normal screens** (≥900px). An open menu shifts the toolbar, slide viewport, and bottom nav bar over by the menu's width via CSS. It must never float on top of the slide content — that's a bug that was hit and fixed; don't reintroduce a plain overlay on wide screens.
- **Overlay + dimmed backdrop only below 900px**, where there's no room to push. Backdrop is `display: none` above that breakpoint.
- **Clicking a menu item does not close the menu** on wide screens — just navigates and sets the clicked item active. Auto-close only on narrow/overlay screens.
- Toggled by a round `☰` button fixed top-left (`#menu-toggle`), independent of the bottom nav.
